Впечатления о парном программировании при разработке микросервисов на Java и Go

## 1. Какую задачу реализовывали?
Мы работали над созданием и интеграцией микросервисов, используя Java (Spring Boot) и Go (Gin). Задача включала разработку REST API, настройку взаимодействия между сервисами через HTTP/gRPC, обработку асинхронных сообщений с помощью Kafka (для Java) и NATS (для Go), а также написание unit- и интеграционных тестов. Парное программирование помогло нам быстрее решать проблемы, связанные с настройкой взаимодействия между сервисами, и эффективно устранять баги.

---

## 2. Какой стиль показался более приемлемым? Почему?
Мы попробовали два стиля парного программирования:

- **Ведущий-ведомый** — один программист (обычно более опытный) направляет процесс, дает рекомендации и помогает с архитектурными решениями, а второй (менее опытный) пишет код. Этот подход был полезен на этапе настройки инфраструктуры микросервисов (например, при конфигурации Docker, Kubernetes или работы с инструментами CI/CD).
- **Пинг-понг** — один программист пишет тест (например, unit-тест для эндпоинта в Java с использованием JUnit или в Go с использованием встроенной библиотеки `testing`), а второй реализует функциональность под этот тест. После этого роли меняются.

Нам больше подошел стиль **Пинг-понг**, так как он:
- Способствовал лучшему пониманию логики микросервисов и их взаимодействия.
- Позволял равномерно распределять нагрузку между участниками.
- Обеспечивал структурированный подход к разработке через TDD (Test-Driven Development), что особенно важно для микросервисов, где надежность и тестируемость критически важны.

Однако стиль "Ведущий-ведомый" оказался полезным на начальных этапах, когда один из участников был менее знаком с экосистемой Go или настройкой gRPC.

## 3. Что получилось? Положительные впечатления
- **Улучшилось качество кода.** Постоянное обсуждение позволило создавать более читаемые и поддерживаемые микросервисы. Например, мы лучше структурировали обработку ошибок в Go (используя стандартный подход с `if err != nil`) и в Java (с использованием `@ExceptionHandler`).
- **Быстрее находили ошибки.** Например, при настройке взаимодействия между сервисами через gRPC мы оперативно обнаружили проблемы с сериализацией/десериализацией данных благодаря совместному анализу логов.
- **Ускорили разработку тестов.** В стиле "Пинг-понг" один участник писал тесты для эндпоинта (например, проверка валидации входных данных), а второй реализовывал логику, что позволило быстрее покрывать функциональность тестами.
- **Получили новый опыт.** Один из нас лучше освоил Spring Boot, а другой — работу с Gin и инструментами Go, такими как `go mod` и `cobra`.
- **Улучшили навыки общения.** Совместная работа над микросервисами требовала четкого обсуждения контрактов API, схем данных и архитектурных решений.

## 4. Что не получилось? Как можно это поправить?
- **Разногласия по архитектуре.** Возникали задержки из-за споров о том, как лучше организовать взаимодействие между микросервисами (например, использовать ли REST или gRPC, синхронное или асинхронное взаимодействие).
    - **Решение:** Заранее обсуждать архитектурные решения и фиксировать их в виде схем (например, с помощью инструментов вроде PlantUML или draw.io).

- **Неравномерная нагрузка.** Иногда один из участников брал на себя больше работы, особенно при настройке инфраструктуры (например, написание Dockerfile или Helm-чартов).
    - **Решение:** Четче разделять задачи и вовлекать обоих участников. Например, один пишет код сервиса, а второй настраивает CI/CD-пайплайн.

- **Сложности с адаптацией к стилю кода.** В стиле "Пинг-понг" временами было сложно адаптироваться к стилю партнера, особенно при работе с Go, где подход к обработке ошибок и структуре кода отличается от Java.
    - **Решение:** Заранее договориться о код-стайле (например, следовать рекомендациям Effective Go для Go и Spring Coding Conventions для Java). Также полезно использовать линтеры (например, `golangci-lint` для Go и Checkstyle для Java).

- **Проблемы с тестированием.** Интеграционные тесты для микросервисов (например, с использованием Testcontainers для Java или `docker-compose` для Go) иногда требовали больше времени, чем ожидалось.
    - **Решение:** Заранее подготовить шаблоны для тестов и договориться о подходе к их написанию (например, использовать библиотеки вроде WireMock для моков внешних зависимостей).

---

## 5. Будете ли использовать парное программирование для других задач? Каких?
Да, парное программирование показало себя полезным инструментом, особенно для следующих задач:

- **Разработка сложных микросервисов.** Например, реализация сервисов с высокой нагрузкой, где требуется настройка кэширования (Redis), балансировки (Kubernetes) и мониторинга (Prometheus/Grafana).
- **Написание тестов.** Парное программирование идеально подходит для TDD при разработке unit- и интеграционных тестов для микросервисов.
- **Настройка инфраструктуры.** Например, совместная работа над Dockerfile, Helm-чартами или настройкой CI/CD-пайплайнов (GitHub Actions, GitLab CI).
- **Проектирование архитектуры.** Обсуждение и реализация контрактов API, схем данных и взаимодействия между сервисами (REST, gRPC, асинхронные очереди).
- **Обучение и обмен знаниями.** Один участник может быть более опытным в Java/Spring, а другой — в Go, что позволяет эффективно делиться опытом.

В целом, парное программирование оказалось полезным опытом, особенно для задач, связанных с микросервисами, где важны надежность, тестируемость и правильная архитектура.
